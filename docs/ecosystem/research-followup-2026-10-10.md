# Plugin ecosystem patterns for KPTAS

**Research captured:** 2026-10-10. Primary product and developer documentation was preferred; marketing statements are treated as claims, not independently measured results. This is ecosystem research, not a runtime acceptance report.

## LobeChat then and LobeHub now

The useful historical comparison is LobeChat in 2023–2024, not a claim that its architecture stayed fixed. Its early extension surface centered on function-calling plugins: a separate plugin index repository exposed a JSON catalog, with entries such as search, weather, and game-information tools; a plugin SDK/template and gateway supported authoring and execution. Users installed a plugin from the store or a custom source, enabled it for a particular assistant, and supplied per-plugin settings. The catalog’s dated records make this phase concrete: the index lists releases from August 2023 through May 2024, including publisher, description, and tags ([historical plugin index](https://github.com/lobehub/lobe-chat-plugins), [historical user flow documentation mirror](https://github.com/isichan0501/lobe-chat/blob/main/docs/Usage/Plugins.md), [early plugin SDK releases](https://github.com/lobehub/chat-plugin-sdk/releases)).

By October 2026, the project has rebranded as LobeHub and describes a broader “agent operator”: agents are the units users create, organize, schedule, and combine; agent groups collaborate; the ecosystem includes a marketplace, skills, and MCP-compatible tools. Its current repository still lists plugins as an ecosystem surface, while highlighting one-click MCP installation and an MCP marketplace ([current LobeHub README](https://github.com/lobehub/lobe-chat), [current agent index](https://github.com/lobehub/lobe-chat-agents)). The shift is from “give this assistant a callable tool” toward “discover, configure, and operate reusable agents and capability bundles.” The transferable lesson is to make discovery and composition visible in the product, not merely to expose an install endpoint. LobeHub’s current README is actively changing; its feature descriptions should be rechecked before implementation decisions.

## Nine adjacent ecosystems

| Ecosystem | Concrete pattern | What transfers to KPTAS |
|---|---|---|
| [VS Code](https://code.visualstudio.com/api/references/extension-manifest) | A manifest declares identity, SemVer, host compatibility, categories, contributions, dependencies, and extension packs. The marketplace supports search, categories, popularity, recency, recommendations, installed/enabled state, versions, and uninstall. Packs can install independent extensions together without coupling their lifecycles ([marketplace UX](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace)). | Use explicit contribution manifests and compatibility metadata. Model a pack as a curated install set, not a monolith; keep constituent packages independently manageable. Make discovery filters and installed state first-class. |
| [Home Assistant](https://developers.home-assistant.io/docs/core/integration/config_flow/) | Integrations expose a guided setup flow, validate connections before setup, store versioned configuration, migrate old entries, support reconfiguration/removal, and document recovery. A tiered quality scale covers ownership, dependency transparency, diagnostics, docs, and entities disabled by default when they are noisy or less common ([quality scale](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/)). | Give each extension a guided capability/configuration flow, versioned settings and migrations, and a visible health state. Avoid activating every available pane by default; let optional capabilities be discovered and enabled intentionally. |
| [Open WebUI](https://docs.openwebui.com/features/extensibility/plugin/) | Community capabilities include tools, pipes, filters, actions, and events, with a community catalog and one-click import. The project explicitly warns that these execute arbitrary Python on the server and that listings/popularity are not security review ([community guidance](https://docs.openwebui.com/features/extensibility/community/)). | Strong composability helps discovery, but never imply a catalog is a sandbox. KPTAS extensions need a capability/permission boundary and must display whether a package executes trusted host code, isolated browser code, or declarative contributions. |
| [Dify](https://docs.dify.ai/en/develop-plugin/publishing/standards/contributor-covenant-code-of-conduct) | Marketplace publication has an explicit quality and privacy bar: meaningful distinct capability, end-to-end readiness, setup instructions, useful failure messages, credential handling, privacy declarations, support/maintenance, and breaking-change notices. | Use publication review as a quality gate and expose maintenance/support signals. Avoid duplicate packages and metadata-only releases; record deprecation and migration paths. |
| [Claude Code](https://code.claude.com/docs/en/plugins) | Plugins bundle multiple contribution types (skills, agents, hooks, MCP servers and LSP configuration); marketplaces are sources for these bundles. The user-facing product supports scopes and lifecycle operations rather than treating all additions as permanently ambient. | Support higher-order packages containing optional components while preserving package-level lifecycle controls. Keep global runtime APIs small and let extension packages add focused workflows. |
| [GitHub Copilot](https://docs.github.com/en/copilot/concepts/agents/about-plugins) | A portable plugin manifest can bundle skills and MCP servers with client-specific contributions. Marketplaces can be remote Git repositories or local directories; install, update, list, enable, disable, and uninstall are separate operations. Catalog versioning supports reproducible team setups ([SDK plugin directories](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/plugin-directories)). | Favor a portable manifest plus namespaced host-specific contributions. Provide profiles/lockfiles so shared setups resolve to the same versions and do not depend on ambient machine state. |
| [Obsidian](https://obsidian.md/help/plugin-security) | Community plugins are disabled behind Restricted Mode by default. The directory supports claiming ownership, reviewing releases, scanning versions, scorecards, and manual review for popular/flagged items. The project is candid that plugins inherit broad app access, so it does not pretend its model is a fine-grained sandbox ([directory workflow](https://docs.obsidian.md/community-directory)). | Make the safe/default state meaningful; communicate actual authority rather than decorative “verified” badges. Show publisher ownership, version-specific scan/review status, and make global disable/recovery easy. |
| [Chrome extensions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions) | Required and optional permissions are declared separately; optional access can be requested only when a feature is used. Changes to host permissions produce user-visible warnings. | Declare extension permissions as structured metadata; request privileged game, filesystem, network, or memory access only when the relevant action is invoked. Explain the purpose in product language and retain revocation controls. |
| [Raycast](https://developers.raycast.com/information/security) | The host controls the extension runtime and exposes a defined API via RPC; extensions run in isolates with resource limits. Its store reviews source and validates packages, while private organization stores support team discovery. It also provides encrypted per-extension secrets/storage and automatic updates. | Separate a minimal host API from extension code, isolate packages where feasible, scope secrets/state by package, and support private/community catalogs. Do not equate an isolate with a complete security boundary: still enforce capabilities and audit host calls. |

## Recommended KPTAS shape

### 1. Keep core small; make Debug and TAS opt-in

The base application should own the game session, renderer/host adapter, stable extension APIs, dock layout, package manager, and generic lifecycle. It should not instantiate score editing, transport/timeline, branches, or debugger panes merely because the host knows those panels. A clean profile should show the game and only the base session/status surfaces. A stored layout may restore a pane only when its owning package is installed, enabled, and the active adapter advertises the required capability.

Ship **Debug** as an optional package that contributes generic inspection workspaces: registers/context, disassembly, memory map/hex view, search, watches, breakpoints, threads, modules, call stack, event/exception log, and command console. Each contribution must be backed by a real adapter capability and reader/action; otherwise it should be absent or visibly unavailable in the package manager, not rendered as a fake empty widget. This draws from IDE-style contribution points and Home Assistant’s capability/configuration model.

Ship **TAS** as a separate optional package. It contributes score authoring, input lanes, transport, seek/step controls, branches, playback state, and TAS-specific metrics. Its dependency should be expressed in the manifest against the minimal stable session/input/time APIs it needs (and, where necessary, the Debug package’s public state APIs), not by embedding Debug and not by making TAS panes part of core. Users can install Debug without TAS and TAS without unrelated debugger panels. A “TAS workspace” pack can recommend/install the relevant subset while each package remains independently disableable/removable, following the VS Code pack distinction.

### 2. Version a narrow extension contract

Use a machine-readable manifest with at least: reverse-domain package ID, display name/icon/summary, author and source repository, license, version, host API range, supported runtime/adapter IDs, contributed panes/commands/menus/metrics, required and optional capabilities/permissions, dependencies and conflicts, data schema version/migrations, update channel, and integrity/signature metadata. Validate manifests before activation. Namescope contributions to prevent collisions. Expose UI contributions declaratively where possible; use a typed host API for data/actions. Keep privileged operations in the host adapter so an extension cannot claim a memory-read or input-write ability it does not actually have.

Treat package lifecycle as distinct states: **available → installed → enabled → configured → active**. Disable must stop activation but preserve data; uninstall must offer whether to retain settings; update should show version/change details and allow rollback; profiles should pin exact versions. Optional permissions are granted at first use, scoped to the package/session, logged, and revocable. For extensions with executable code, use isolation plus explicit host-call grants; a browser Worker alone is not a security sandbox for host-provided privileged operations.

### 3. Make the hub a discovery graph

Catalog cards should quickly answer “what does it add?” with a distinctive icon/preview, one-line outcome, screenshots or a live sample, supported games/adapters, capability coverage, and install state. Mix recommendation surfaces: compatible with current game/runtime; trending/recently updated; related packages; installed-together; dependency/dependent graph; collections; official/recommended; and “complete this setup” suggestions. Include favorites, save for later, personal collections, exportable profiles, and community packs. Show author/source, last release/maintenance state, version history, API compatibility, permissions, data handling, conflicts, dependencies, and review/scanner results beside the install action. “Popular” is a discovery signal, never a trust claim.

### 4. Win loyalty by reducing uncertainty and friction

The research supports stickiness through excellent defaults, visual identity, easy discovery, composable packages, shareable profiles, and predictable updates—not through incompatible formats or traps. Keep packages inspectable, portable and reversible. Provide local package sources for development; a signed official catalog and community catalogs; a no-network/local mode; and an export that records package IDs, exact versions, source and configuration. Make it easy to publish small extensions by giving creators templates, SDK examples, local hot reload, capability mocks, preview cards, and automatic manifest checks.

## Applying REA

[REA’s project documentation](https://github.com/morluto/rea) describes local inspection tools for native, managed, Electron/JavaScript and browser applications, and emphasizes evidence/limitations rather than source-code recovery. It can help study implementations or verify observable behavior when source access is unavailable. For the open-source ecosystems above, their official docs and manifests already expose the relevant contracts; REA is not needed to reverse-engineer them, and should not be used to copy protected assets or assume decompilation reconstructs original source.
