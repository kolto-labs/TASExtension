# Statis / TelosCORE extension ecosystem research

Research date: 2026-10-10. Scope: ten ecosystems, their extension lifecycle, discovery, composition, trust, and implications for this project. This is research and an implementation recommendation; it does not claim that the proposed services or permissions already exist in Statis.

## Main recommendation

Use TelosCORE as the runtime and capability broker, Statis as the workbench, and independently installed packages as the owners of commands, views, settings, and workflows. Make `telos.debug` and `telos.tas` separate packages. A TAS extension pack can depend on debugger capabilities without making every debugger workspace a TAS workspace. Score editor, input roll, transport timeline, branches, and recording export belong to TAS. Memory, registers, threads, modules, disassembly, breakpoints, symbols, and inspection belong to Debug.

Installing a package, enabling it in a profile, activating its code, and showing its panels are four different operations. None should implicitly stand in for the others. An installed but disabled TAS package contributes no panels or hotkeys. Enabling it may register its views, but opening all of them should require choosing the TAS workspace or an explicit user action. The default game workspace should remain small.

The most useful combination is VS Code's declarative contribution model, Raycast's constrained command/UI API, Dify's brokered services and local development connection, Chrome's explicit capability permissions, and Home Assistant's distinction between required dependencies and optional companions. This combination is our synthesis, not an existing universal standard.

## Research method and currency

The provided skill inventory was checked first; the technical-plan skill supplies planning process rather than an ecosystem specification. Project-local `.agents`, `.codex`, and `.claude` skill directories were absent in this checkout. Context7 CLI was unavailable. Research therefore used official documentation, vendor engineering posts, official repositories, and dated release notes. No runtime SDK was installed, no tests/builds/deployments were run, and no frontend files were changed.

Deprecation checks were performed before considering API adoption. Important findings: Chrome currently documents Manifest V3 as its supported manifest version; older Dify plugin documentation explicitly redirects as deprecated documentation; current Open WebUI documents native function calling as the supported mode; current Claude Code documentation lives at `code.claude.com`, and older Anthropic URLs can describe older behavior. No third-party API is proposed as a mandatory dependency of TelosCORE. Pin implementation integrations to concrete upstream versions and recheck their release notes when that work starts. [Chrome manifest](https://developer.chrome.com/docs/extensions/reference/manifest), [Dify old documentation notice](https://dify-6c0370d8.mintlify.app/en/plugins/publish-plugins/publish-to-dify-marketplace), [Open WebUI tools](https://docs.openwebui.com/features/extensibility/plugin/tools/), [Claude plugin reference](https://code.claude.com/docs/en/plugins-reference).

## Ten ecosystems

### 1. LobeChat / LobeHub

**Historical evidence:** LobeChat's official late-2023 changelog records a plugin store, a plugin detail modal, OpenAPI authentication/schema support, and plugin settings. Its 2024 overview lists plugins and an assistant market; an August 31, 2024 design post says knowledge can be attached to a particular assistant and toggled in the same manner as plugins. That is the useful historical interaction pattern: discover globally, configure once, enable in context. These are dated official descriptions, not a recreated pixel-perfect historical UI. [Plugin-era changelog](https://lobehub.com/pl/changelog/2023-12-22-dalle-3), [2024 overview](https://lobehub.com/tr/docs/usage/start/), [2024 knowledge design](https://lobehub.com/pt-BR/blog/knowledge-base/).

**Current evidence:** LobeHub's repository now emphasizes agents, agent groups, and MCP-compatible tools/skills. Marketplace detail pages expose category, author, version, verification status, installation, capabilities, related recommendations, and version history. Its legacy plugin index remains a separate catalog repository. JSON Schema settings can generate configuration controls and route a missing-setting error directly into a configuration card. These do not establish a universal dependency solver or sandbox for all plugins. [Current repository](https://github.com/lobehub/lobehub), [catalog](https://github.com/lobehub/lobe-chat-plugins), [SDK settings](https://chat-plugin-sdk.lobehub.com/quick-start/plugin-settings), [marketplace detail example](https://lobehub.com/mcp/artemida1609-mcp-service).

**Apply:** visually identifiable cards and contextual enablement; keep configuration repair inside the extension flow. Do not copy current marketing claims as implementation guarantees.

### 2. Visual Studio Code

Extensions declare identity, engine compatibility, commands, settings, views, and other contributions in `package.json`. Dependency relationships and extension packs are separate concepts. The Marketplace surfaces publisher, description, popularity/rating, source links, and workspace recommendations; users can install, disable, uninstall, and select versions. These controls are the closest match to a debugger workbench with optional TAS packs. [Manifest](https://code.visualstudio.com/api/references/extension-manifest), [Marketplace](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace).

Browser extensions have a `browser` entry point in a worker, whereas native Node extensions use `main`; both can share declarative contributions and APIs. This preserves one visual contract across browser/native while acknowledging different runtime capabilities. The browser sandbox is meaningful; native extension execution does not imply fine-grained confinement. [Web extensions](https://code.visualstudio.com/api/extension-guides/web-extensions).

**Apply:** package-owned dock views, commands and hotkeys; stable public contribution points; profile/workspace enablement; separate executable adapters with one shell. A package pack should aggregate packages rather than duplicate their code.

### 3. Open WebUI

Open WebUI distinguishes model-callable Tools from Functions that alter application behavior: Pipes add providers, Filters intercept messages, Actions add controls, and Events expose lifecycle behavior. Settings and rich UI are first-class extension surfaces. Functions are cached and reloaded when source changes. Its current documentation explicitly warns that these Python extensions execute with server privileges and restricts creation to administrators. [Functions](https://docs.openwebui.com/features/extensibility/plugin/functions/), [tool taxonomy](https://docs.openwebui.com/features/extensibility/plugin/tools/).

**Apply:** distinguish runtime adapters, analysis tools, event processors, and UI contributions instead of treating every package as a free-form script. Useful hot reload requires precise lifecycle/disposal handling. Do not adopt unrestricted in-process server execution as the default community trust model. The documented taxonomy alone does not prove dependency resolution, safe rollback, or arbitrary package isolation.

### 4. Dify

Dify's March 4, 2025 engineering account describes extracting previously coupled model/tool modules into independently installable runtimes and a marketplace. Local plugin debugging uses a persistent connection to forward requests to development code, avoiding repackaging on every edit. This directly addresses our rebuild bottleneck. [Plugin system engineering](https://dify.ai/blog/dify-plugin-system-design-and-implementation).

Host-mediated reverse invocation lets a plugin call platform App, Model, Tool, and Node services, including other tool plugins; bundles compose related functionality. It is a better model for Debug/TAS interoperability than modules importing each other's internal files. [Reverse invocation, modified June 24, 2026](https://docs.dify.ai/en/develop-plugin/features-and-specs/advanced-development/reverse-invocation).

Marketplace requirements include support contacts, meaningful version changes, privacy declarations, migration/deprecation notices, and maintenance-risk labels; neglected packages may be restricted or removed. [Publishing requirements](https://docs.dify.ai/en/develop-plugin/publishing/standards/contributor-covenant-code-of-conduct).

**Apply:** live development connection, brokered capabilities, explicit maintenance status. Preserve our own package identity/API contracts rather than depending on Dify's internal daemon.

### 5. n8n

n8n exposes community nodes at the point where a workflow author searches for a missing node. Verified matches appear in the node picker; the detail view lists supported actions and allows installation. Instance administrators manage installation; other members use installed nodes. Packages can be removed through Community Nodes settings. [Verified-node workflow](https://docs.n8n.io/integrations/community-nodes/installation-and-management/install-verified-community-nodes.md).

The official risk documentation says ordinary community nodes can access the host and workflow data, and updates can break workflows. Verification adds review, not a universal sandbox. [Community risks](https://docs.n8n.io/integrations/community-nodes/risks).

**Apply:** searching a missing debugger capability should offer compatible installable additions in context. Keep credential requirements visible. Saved workflows must preserve node/package versions so an update does not silently change an old run or analysis.

### 6. Raycast

Raycast extends npm's manifest with title, icon, categories, supported platforms, commands, preferences, and AI tools. Commands use common view/action patterns rather than forcing every extension to invent an application shell. [Manifest](https://developers.raycast.com/information/manifest).

Its public extensions are source-reviewed before publication. The runtime uses a managed Node process, per-extension V8 isolates, and a defined RPC API. The official document explicitly says file/network access is not further sandboxed; isolate separation must not be confused with permissions confinement. Installed packages are archived artifacts and updated automatically. [Security model](https://developers.raycast.com/information/security), [Publishing](https://developers.raycast.com/basics/publish-an-extension).

**Apply:** common lightweight command components, managed runtime, source links, concise setup, and per-package storage. Add our own enforceable permissions and reproducible version pins because automatic updates alone do not meet TAS replay requirements.

### 7. Obsidian

Obsidian's manifest declares a stable ID, semantic version, minimum app version, description, author, funding, and desktop-only compatibility. The official sample shows a small manifest rather than a giant custom package descriptor. This is a good template for narrow additions and browser/native compatibility flags. [Manifest reference](https://docs.obsidian.md/Reference/Manifest), [sample manifest](https://raw.githubusercontent.com/obsidianmd/obsidian-sample-plugin/master/manifest.json).

**Apply:** low publishing overhead, descriptive metadata, compatibility filtering, persistent per-package settings. The reviewed manifest does not define dependency solving or a permission sandbox; do not infer these from its community catalog. A plugin API can remain small while extensions build substantial functionality, provided lifecycle cleanup is enforced by the host.

### 8. Chrome extensions

Manifest V3 declares entry points, actions, commands, side panels, options, service workers, and permissions. Permissions distinguish extension APIs from host access, and optional permissions can be requested when needed instead of all at installation. [Manifest](https://developer.chrome.com/docs/extensions/reference/manifest), [permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions).

**Apply:** declarative required/optional capabilities with contextual consent; predictable UI entry points; no side effects merely because a package is present. Keep host access narrow: memory reading, memory writing, execution control, file access, network destinations, and native adapters must be different grants. These are Statis-specific proposed permissions, not Chrome permissions. A revoked capability should actually stop the associated operations, not merely remove a badge.

### 9. Home Assistant

Its integration manifest separates required integrations (`dependencies`) from optional ordering (`after_dependencies`), pins Python requirements, identifies owners, and declares configuration flows and discovery metadata. Required setup ordering does not guarantee that all dependency configuration entries are ready. That subtlety matters: installing a debugger provider is different from attaching it to a usable game session. [Integration manifest](https://developers.home-assistant.io/docs/creating_integration_manifest/).

**Apply:** represent required dependencies, optional companions, setup prerequisites, and active-session readiness separately. An extension can be installed and enabled while waiting for a game or permission without pretending its controls work. Use configuration flows to guide setup and capability status to decide when commands become available.

### 10. Claude Code plugins

Plugins bundle namespaced skills, commands, agents, hooks, MCP/LSP servers, settings, and user configuration. Current manifests include enablement and dependency fields; user enablement survives updates. Catalog metadata and runtime component fields have distinct roles. [Plugin reference](https://code.claude.com/docs/en/plugins-reference).

Marketplaces use a lightweight catalog that points to local, Git, archive, or npm sources. They support private distribution and local development; locally installed source can reload without a version bump, while hosted installs use cached copies. [Marketplace creation](https://code.claude.com/docs/en/plugin-marketplaces).

**Apply:** composable packs that can include UI, tools, workflows, and documentation while retaining namespaced identity; local development versus published package resolution; private registries. Agent instructions and executable hooks require different trust treatment. Do not treat a human-readable skill file as a permission boundary.

## Proposed Statis package contract

This contract is a design proposal. Use JSON Schema and a versioned, language-neutral host protocol. Compile-time types are helpful authoring aids but cannot replace runtime capability enforcement.

```json
{
  "schemaVersion": 1,
  "id": "telos.tas",
  "version": "0.1.0",
  "name": "TAS",
  "engine": { "telosCore": ">=0.1 <0.2" },
  "defaultEnabled": false,
  "dependencies": { "telos.debug": ">=0.1 <0.2" },
  "optionalDependencies": {},
  "requiresCapabilities": ["execution.pause", "execution.step", "input.inject"],
  "optionalCapabilities": ["snapshot.restore", "capture.video"],
  "entrypoints": { "browser": "dist/browser.js", "native": "dist/native.js" },
  "contributes": {
    "views": ["tas.score", "tas.inputs", "tas.timeline", "tas.branches"],
    "commands": ["tas.record", "tas.play", "tas.seek"],
    "workspaces": ["tas.authoring"]
  }
}
```

The example illustrates names and ownership, not the complete final schema. A separate `telos.tas-pack` should name the TAS package and companions plus a recommended workspace; it must not implicitly enable unrelated packages. Version constraints must use an implemented resolver rather than unchecked strings.

Lifecycle: discover → inspect → resolve → verify artifact → stage → grant permissions → enable in profile → activate on compatible session → deactivate → disable/remove. Keep installed versions, profile locks, migration receipts and rollback data. Updates should stage before activation; permissions newly requested by an update require a new decision. Deactivation must unregister commands, hotkeys, subscriptions, dock views and background tasks, and release injected inputs. Removing an extension should preserve its user data until explicitly discarded.

Capabilities should be brokered requests with explicit version, session identity, cancellation, bounded payload, and structured result. Backend adapters expose supported operations; the workbench must not imply that every uploaded binary supports every debugger action. A package supplies views only for capabilities it can actually use. UI hot reload should dispose and recreate package views without restarting the game; runtime adapter changes may still require a coordinated restart.

## Discovery hub and trust

Use **Telos Exchange** as a working name, subject to naming review. Give every card a clear icon, one-sentence outcome, screenshots or preview, compatibility, installed/enabled state, maintained/verified status, version/update date, source/license, permission summary, and author. Badges need evidence and definitions: source-available, reviewed, signed, compatible, and popular mean different things.

Provide overlapping routes: current-session compatible, recommended for profile, recently updated, new, trending with a stated time window, category/capability, collections, dependents, companions, and “complete your setup.” Dependencies and “commonly installed together” must be visibly different. Recommendations should explain relevance and never silently install extras.

Allow save/favorite/wishlist, personal and shared collections, import/export of profiles and version locks, missing-package completion status, conflict explanations, and one-action disable. Publishing should accept a narrow useful package with documentation, screenshot, compatibility declaration, source/license information and reproducible artifact. Reviews and conflict reports need package/version/game-adapter scope so obsolete reports do not condemn current releases.

The sustainable adoption strategy is an excellent stable API, fast development reload, useful bundled packages, reliable compatibility, and a rich community graph. Deliberate incompatibility or trapping users makes maintenance harder and undermines creator confidence. Keep project/recording/profile exports usable independently of the catalog, while making this platform the easiest place to develop and combine extensions.

## Implementation sequence after browser-game acceptance

1. Fix package ownership and default visibility now: TAS contributions only exist for an enabled TAS package; persisted layouts cannot resurrect disabled-package panels.
2. Establish one contribution registry for dock views, commands, hotkeys, settings and workspaces, shared by native and browser hosts.
3. Make Debug a real capability-backed package, starting with session state, memory inspection, threads/modules and breakpoints supported by the current adapter. Inventory the x64dbg/Ghidra/IDA/Cheat Engine surfaces separately; implementing empty imitations is not equivalence.
4. Add lifecycle disposal, profile enablement, dependency resolution, versioned artifacts and rollback before opening community installation.
5. Add developer reload and source diagnostics; then build catalog discovery, collections, permissions review and publishing.

This work must not delay the immediate critical path: a stable, playable KOTOR session inside the existing local browser page. Research and package-default work can proceed independently; runtime rebuilds should be coordinated and batched.
